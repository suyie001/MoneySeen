# MoneySeen

> 上传支付账单，把模糊的流水整理成看得懂、可修正、可追溯的个人财务报告。

MoneySeen 是一款移动优先的跨平台个人账目分析应用。Flutter 客户端覆盖 Web、iOS 和 Android；用户无需从零开始逐笔记账，只需导入微信支付等平台导出的账单，系统便会识别交易、去重、使用规则与大模型进行分类，并从收入、支出、交易对象、项目、标签和时间等角度生成报告。

第一版首先满足个人使用，同时按照公开产品和应用商店发行的标准设计。产品初期无需注册，以设备本地数据为主；后续可扩展账户系统、云端长期保存、跨设备同步，以及支付宝、银行卡和信用卡账单。

## 产品状态

当前已完成 MVP 基础架构，并打通第一条真实可用链路：微信支付 XLSX
账单选择、本地解析、导入预览、交易单号去重和 Drift 本地入库。

已使用一份包含 165 笔流水的真实微信账单完成只读验收，解析笔数及收入、
支出、中性交易合计均与微信账单摘要一致。真实个人账单不会进入仓库或测试夹具。

代码将公开托管，并以同一套 Flutter 客户端发布 Web 版、App Store 版和 Google Play 版。详细技术设计见 [系统架构](docs/architecture.md)。

开发环境、运行方式与质量检查见 [开发指南](docs/development.md)。

第一版的目标不是成为完整的复式记账或资产管理软件，而是把“导出的支付流水”快速转化为可信、可探索的账目数据。

### 当前可以体验

1. 运行 Flutter Web、iOS 或 Android 应用。
2. 在首页选择“导入微信账单”。
3. 选择微信支付导出的 `.xlsx` 文件。
4. 查看账单区间、可导入数量、重复数量、收入、支出和前 20 笔流水。
5. 确认后将非重复流水写入当前设备的本地数据库。

下一阶段将实现交易明细、人工分类及第一版筛选报表。

## 为什么做 MoneySeen

支付平台能够导出完整流水，但原始账单通常存在以下问题：

- 商户、个人转账、红包、退款和提现混杂在一起。
- “资金流出”不等于“消费”，“资金流入”也不等于“收入”。
- 个人转账通常缺少有效的商品和用途信息。
- 同一个交易对象可能对应固定用途，也可能需要逐笔区分。
- 微信、支付宝和银行账单字段不同，同一笔资金移动还可能在多个来源中重复出现。
- 普通用户很难通过电子表格完成长期分类、筛选和趋势分析。

MoneySeen 的核心价值不是展示几张图表，而是帮助用户建立一套越用越准确的个人账目解释体系。

## 产品原则

### 1. 先保证账目含义正确，再计算报表

系统必须区分原始资金方向和用户认定的账目性质。例如提现、信用卡还款和账户互转属于资金移动，不应直接计入消费或收入。

### 2. 自动处理与人工决定并存

大模型和规则负责减少重复劳动，用户始终拥有最终决定权。用户的明确修改和自定义规则优先于系统建议。

### 3. 分类不只有一个维度

一笔账目可以同时拥有固定分类、自定义项目和多个标签。例如：

```text
医疗 / 家庭 / 给父母买药
```

其中“医疗”是分类，“家庭”是项目，“给父母买药”可以是标签或用途备注。

### 4. 方便好用优先

面向个人用户时，减少操作成本比追求绝对封闭的数据环境更重要。第一版默认使用云端大模型提供分类建议，但需要清楚告知用户哪些信息会被处理，并尽量排除交易单号、银行卡号等分类不需要的字段。

### 5. 原始数据可追溯

标准化、分类、拆分和人工修改不能破坏原始账单。任何派生结果都应能追溯到来源文件和原始交易。

### 6. 从第一天支持多来源扩展

微信支付只是第一个导入适配器。标准数据层不能绑定微信字段，后续应能接入支付宝、银行卡和信用卡账单。

## 关键概念

### 原始方向

由账单来源提供，不由用户修改：

- 流入
- 流出
- 中性或未知

### 账目性质

表达这笔交易在个人账目中的真实含义：

- 消费
- 收入
- 账户间转移
- 退款
- 报销
- 借出
- 借入
- 借款归还
- 其他

“流入/流出”用于描述现金流，“收入/消费”用于描述经济含义，两者不能混为一谈。

### 分类、项目和标签

- **分类**：稳定的统计口径，如餐饮、购物、住房、交通、医疗、教育。
- **项目**：用户自定义的阶段性用途，如一次旅行、装修、经营活动。
- **标签**：可以多选的补充维度，如家庭、工作、可报销、冲动消费。

系统提供基础分类，用户可以新增、修改、停用分类及子分类。项目和标签完全由用户自定义。

### 账本、账户和数据来源

- **账本**：个人、家庭、经营等相互独立的分析空间。
- **账户**：微信零钱、某张银行卡、某张信用卡等资金载体。
- **数据来源**：微信账单、支付宝账单、银行账单等导入渠道。

一笔交易默认只属于一个账本。跨账本场景通过拆分交易处理。

## 目标用户

- 想知道钱主要花到哪里、从哪里获得，但不愿每天手工记账的人。
- 有大量微信转账、红包或二维码交易，需要按交易对象整理用途的人。
- 同时存在个人、家庭或经营账目，希望自定义统计口径的人。
- 希望导入多个平台账单并统一分析的人。

## MVP 用户流程

```text
打开应用
  → 上传微信支付账单
  → 本地解析并检查文件
  → 标准化、去重并识别结构性交易
  → 应用用户规则
  → 使用大模型分类剩余交易
  → 集中处理待确认项
  → 查看和筛选报表
  → 保存规则、备份或同步数据
```

导入完成后不能只显示“成功”。系统应提供处理摘要，例如：

```text
共导入 165 笔
已确认 120 笔
建议分类 30 笔
待分类 15 笔
跳过重复记录 0 笔
```

## 信息架构

### 欢迎与账单上传

- 简短说明产品价值和隐私处理方式。
- 支持拖放、文件选择和移动端系统文件选择器。
- 第一版接受微信支付导出的 XLSX 文件。
- 提供示例账单或演示数据，便于用户不上传私人文件也能体验产品。
- 上传前说明文件处理位置以及是否会调用云端模型。

### 数据总览

- 收入、消费、净收支和现金净流量。
- 账户间转移金额。
- 已确认、建议分类、待分类的笔数和金额。
- 主要支出分类、主要收入来源和高频交易对象。
- 日、周、月趋势。
- 异常大额或明显偏离历史习惯的交易。

总览必须同时展示数据完整性，避免在大量账目未确认时给用户造成精确结论的错觉。

### 交易明细

- 按时间倒序展示标准化后的交易。
- 可以快速编辑性质、分类、项目、标签、账本、交易对象和备注。
- 可以查看原始字段、来源文件、分类来源、模型理由和修改历史。
- 支持单笔拆分和撤销拆分。
- 支持批量选择与批量修改。

### 待确认中心

待确认中心是 MVP 的核心工作台，用于集中处理模型不确定或缺少信息的交易。

每笔交易展示：

- 交易时间、方向、金额、交易对象和商品描述。
- 建议的账目性质、分类、项目和标签。
- 建议置信度。
- 简短、可读的建议理由。
- 接受、修改、跳过等操作。

用户修改时可以选择：

- 仅修改这一笔。
- 修改当前选中的多笔交易。
- 修改该交易对象的所有历史交易。
- 将本次操作保存为以后自动执行的规则。

### 报表分析

第一版提供：

- 收入、消费、净收支和现金流总览。
- 按分类和子分类统计支出。
- 按项目和标签统计用途。
- 按交易对象统计付给谁、从谁收到、金额和频率。
- 按日、周、月展示趋势。
- 大额交易和异常波动。
- 分类完成度与待确认金额。
- 当前筛选结果的汇总与占比。

所有报表必须基于同一套筛选状态，并允许点击图表下钻到交易明细。

### 分类、项目和标签管理

- 管理系统基础分类和用户自定义分类。
- 支持二级分类，MVP 暂不提供更深层级。
- 新增、改名、排序、停用项目和标签。
- 删除已被使用的维度前提示影响范围，并提供迁移目标。

### 自动分类规则

- 查看规则名称、条件、结果、优先级、命中次数和最近命中时间。
- 启用、停用、编辑、复制和删除规则。
- 在保存规则前预览会影响哪些历史交易。
- 用户选择后，可将规则应用到历史数据或仅用于未来导入。

### 数据来源与导入记录

- 展示每次导入的来源、文件名、账单区间、导入时间和处理结果。
- 展示新增、重复、失败和待确认的记录数量。
- 支持删除某次导入及其尚未被合并引用的数据。
- 支持重新运行标准化或分类流程。
- 后续支持多个微信号、支付宝账户和银行账户。

### 设置、备份与同步

- 管理账本、账户、基础分类和模型偏好。
- 导出完整的可恢复备份。
- 从备份恢复，并在覆盖前展示影响范围。
- 清空当前账本或全部本地数据。
- 查看当前数据存储位置、模型处理方式和同步状态。
- 配置 Google Drive、iCloud Drive 等可选同步目标。

## 筛选系统

交易明细和报表共用统一筛选模型。MVP 至少支持：

- 时间范围。
- 收入、支出和原始资金方向。
- 账目性质。
- 分类和子分类。
- 项目。
- 标签。
- 交易对象。
- 交易类型。
- 金额范围。
- 账本和账户。
- 数据来源。
- 分类状态：已确认、建议分类、待分类。
- 分类来源：人工、规则、大模型、系统识别。
- 是否为拆分交易、退款或账户转移。

桌面端提供完整筛选面板，移动端采用筛选抽屉和常用快捷筛选。后续支持保存筛选视图。

## 导入与标准化

### 导入架构

```text
原始文件
  → 来源解析器
  → 字段校验
  → 标准交易记录
  → 去重与关联
  → 性质识别
  → 分类
  → 报表
```

每种来源实现独立适配器，不能让来源特有字段直接渗透到报表和分类逻辑。

### 微信支付适配器

第一版需要：

- 识别微信支付账单标题、账单区间和导出时间。
- 解析交易时间、交易类型、交易对象、商品、收支、金额、支付方式、状态、交易单号、商户单号和备注。
- 将 Excel 日期正确转换到原账单时区。
- 保留原始字符串，便于追溯和兼容格式变化。
- 对缺少关键列、无法识别的版本或损坏文件给出明确错误。
- 忽略说明行和空白行，不把账单摘要误认为交易。

### 去重

第一版优先使用来源标识和交易单号构建幂等键。交易单号不可用时，可以结合来源账户、交易时间、方向、金额、交易对象和商户单号生成候选指纹。

系统应区分：

- 确定重复：自动跳过。
- 疑似重复：保留并提示用户确认。
- 多来源关联：后续用于识别同一笔账户转移的两侧记录。

删除导入批次或重新导入不能产生静默重复。

## 分类体系

### 分类状态

- **已确认**：用户确认过，或命中用户创建的明确规则。
- **建议分类**：系统或模型有较高把握，但尚未得到用户确认。
- **待分类**：信息不足、结果冲突或置信度过低。

置信度阈值应可配置，初期可以使用产品默认值。

### 分类流水线

```text
标准交易
  → 结构性交易识别
  → 用户明确规则
  → 已确认历史映射
  → 系统词库与启发式规则
  → 大模型批量分类
  → 结果校验
  → 已确认 / 建议分类 / 待分类
```

提现、充值、信用卡还款等结构性交易应优先由确定性逻辑识别。用户规则命中的结果保持稳定；大模型主要处理缺少明确规则、语义模糊和需要上下文判断的交易。

### 优先级

从高到低：

1. 当前单笔的人工结果。
2. 拆分后的子交易结果。
3. 用户明确创建的规则。
4. 用户已确认的交易对象映射。
5. 系统结构性识别和确定性规则。
6. 大模型建议。
7. 默认未分类状态。

任何重新分类操作都不能静默覆盖更高优先级的结果。

## 大模型分类

大模型分类属于第一版正式能力，而非远期功能。

### 输入

模型可使用：

- 收支方向和金额。
- 交易类型。
- 交易对象。
- 商品描述和用户备注。
- 来源平台。
- 用户可用的分类、项目和标签。
- 相同交易对象的已确认历史摘要。
- 同批次交易的必要上下文。

默认不发送交易单号、商户单号、完整银行卡号或原始文件。若某个字段对分类没有帮助，则不应发送。

### 结构化输出

模型必须返回可校验的结构化数据，至少包括：

```json
{
  "nature": "expense",
  "categoryId": "medical",
  "projectId": null,
  "tagIds": ["family"],
  "confidence": 0.91,
  "reason": "交易对象和历史记录均与中药购买相关",
  "needsReview": false
}
```

所有 ID 必须来自本次请求允许的候选项。服务端或本地校验器负责拒绝未知枚举、无效 ID、缺失字段和越权输出。

### 批量、成本和稳定性

- 对交易进行批量分类，避免逐笔请求。
- 使用标准化交易摘要和分类配置生成缓存键。
- 同一输入在没有规则或模型版本变化时优先复用结果。
- 记录模型提供方、模型版本、提示词版本和分类时间。
- 请求失败时保留交易并进入待分类状态，不阻塞文件导入。
- 分类器通过统一接口接入，后续可切换云端模型或本地模型。

### 用户反馈闭环

用户接受、修改或拒绝建议后，系统应：

- 更新当前交易。
- 询问是否保存为交易对象或关键词规则。
- 更新该交易对象的已确认历史摘要。
- 不自动改变其他已确认交易，除非用户明确授权。

## 规则引擎

MVP 规则条件支持：

- 数据来源。
- 原始收支方向。
- 交易类型。
- 交易对象精确匹配或包含。
- 商品和备注关键词。
- 金额范围。
- 指定账户或账本。

规则结果支持：

- 账目性质。
- 分类和子分类。
- 项目。
- 一个或多个标签。
- 标准化交易对象。

多条规则同时命中时，按照用户优先级和条件具体程度执行。冲突无法自动解决时进入待确认中心，不能随意选择其中一条。

## 交易对象标准化

同一商户或个人可能以不同名称出现，系统需要保留原始名称，并允许映射到统一交易对象。

例如：

- 品牌名、公司主体名和门店名合并为同一商户。
- 微信昵称变化后仍可指向同一个人。
- 用户可以取消合并或仅修改显示名称。

标准化交易对象可设置默认性质、分类、项目、标签及适用账本，但单笔人工结果仍然优先。

## 拆分交易

底层从第一版支持拆分，界面先提供简单入口。

拆分规则：

- 原始交易保持不可变。
- 子交易金额之和必须等于原始交易金额。
- 每个子交易可以拥有独立的性质、分类、项目、标签和备注。
- 报表统计子交易，不重复统计原始交易。
- 撤销拆分后恢复使用原始交易的分类结果。
- 跨账本交易通过拆分后将子交易分别放入不同账本。

## 本地存储、备份与同步

### 第一版存储策略

- 使用跨平台 SQLite 数据层保存标准化交易、分类配置、规则和报表状态；Web 端使用 WebAssembly/IndexedDB 兼容实现。
- 设备本地数据库是无需登录模式下的主数据源。
- 原始 XLSX 文件解析完成后默认不长期保存，只保留导入元数据、文件哈希和必要的原始行数据。
- 提供版本化的完整备份格式，确保以后升级数据结构时可以迁移。

### 可选同步

同步采用独立适配器，不让业务层依赖特定云盘：

- 本地备份文件导出和恢复。
- Google Drive 同步。
- iCloud Drive 文件保存与恢复。
- 后续可增加其他网盘或 WebDAV 兼容存储。

无需 MoneySeen 账户不代表无需第三方授权。Google Drive 等自动同步需要用户授权对应云盘。同步默认关闭，由用户主动开启。

第一阶段可以先通过系统文件选择器将备份保存到 iCloud Drive、Google Drive 或其他文件提供方；自动同步作为后续增量能力。未来原生 App 可使用平台提供的能力增强 iCloud 同步体验。

### 同步冲突

- 备份包含设备标识、数据版本、生成时间和内容摘要。
- 恢复前展示新增、覆盖和冲突数量。
- 默认不静默覆盖本地较新的人工修改。
- 后续自动同步采用记录级版本或操作日志解决多设备冲突。

## 隐私与数据控制

便利性优先不等于隐藏数据处理方式。公开产品至少需要：

- 上传和模型分类前提供简明说明。
- 明确区分本地解析、云端模型处理和云盘同步。
- 默认不将用户账单用于训练公共模型。
- 用户可以关闭模型分类，仅使用规则和手工整理。
- 用户可以删除单个账本、导入批次或全部数据。
- 不在日志和错误监控中记录完整账单内容、交易单号或银行卡信息。
- 大模型请求只包含完成分类所需字段。
- 云盘授权采用最小权限，并允许随时断开连接。
- 未来账户版本提供数据导出和账户彻底删除能力。

## 推荐技术方案

此部分为当前建议，并非不可更改的产品约束。

- 客户端：Flutter、Dart，一套代码覆盖 Web、iOS 和 Android。
- 客户端架构：View、ViewModel、Repository、Service，并为复杂账单流程增加 Domain Use Case。
- UI：移动优先的响应式组件系统。
- 本地数据库：Drift/SQLite；Web 使用 WebAssembly，并按浏览器能力回退到 IndexedDB 持久化。
- 表格解析：设备端 XLSX 解析适配器。
- 数据校验：共享 Schema，同时验证解析结果和模型输出。
- 图表：支持交互、响应式和下钻的图表库。
- 后端：Dart Frog，负责模型代理、限流、防滥用、远程配置及未来的账户和同步能力。
- 大模型：通过 Dart Frog 服务端代理或可替换网关调用，分类器保持提供方无关。
- 同步：统一 `SyncProvider` 接口，对接备份文件、Google Drive 和其他存储。
- 测试：解析器样本测试、规则冲突测试、金额与拆分不变量测试、端到端导入流程测试。

第一版即使无需登录，也不应把模型密钥放入客户端代码。Dart Frog 服务负责匿名安装令牌、限流、模型调用和结构化输出校验，而账本数据仍以本地存储为主。

## MVP 验收标准

### 导入

- 能成功解析受支持格式的微信支付 XLSX 文件。
- 账单交易数量和金额汇总与原文件一致。
- 重复导入同一文件不会生成重复交易。
- 不支持或损坏的文件能给出可行动的错误提示。

### 分类

- 明确的中性交易不会被计入消费或收入。
- 用户规则的结果不会被大模型静默覆盖。
- 模型输出经过结构校验并带有置信度和理由。
- 失败或低置信度结果进入待确认中心。
- 用户可以将一次修改保存为长期规则。

### 拆分与统计

- 子交易金额之和始终等于原始金额。
- 报表不会同时统计原始交易和拆分子交易。
- 所有图表汇总可以下钻并与明细金额核对一致。
- 筛选后的总数、金额和图表使用同一数据集合。

### 数据控制

- 用户可以导出并恢复完整备份。
- 用户可以清空全部数据。
- 刷新页面或关闭浏览器后，本地数据仍然存在。
- 模型调用、云盘授权和同步状态对用户可见并可关闭。

### 响应式体验

- 核心上传、确认、筛选和查看报表流程可在手机浏览器、iOS 和 Android 完成。
- 桌面端能够高效查看明细并执行批量操作。

## 成功指标

MVP 阶段优先关注产品是否真正减少整理成本：

- 首次导入成功率。
- 从上传到看到第一份报告的耗时。
- 自动分类覆盖率与用户接受率。
- 待确认交易处理完成率。
- 用户创建规则后的重复操作减少量。
- 报表下钻和筛选的使用频率。
- 备份成功率和恢复成功率。
